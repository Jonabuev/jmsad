# 🔧 Исправление проблемы с потерей PDF документов при деплое

## Проблема

PDF документы по жалобам не сохранялись при обновлении через CI/CD. Документы просто не отображались после деплоя.

## Причина

В `docker-compose.production.yml` и `dc.prod.yml` была **несинхронизация путей для медиа-файлов**:

- **Бэкенд** использовал именованный Docker volume: `backend_media:/app/media`
- **Nginx** использовал bind mount: `./media:/app/media:rw`

Эти пути не были синхронизированы, и при обновлении через CI/CD:
1. Docker volume `backend_media` мог пересоздаваться
2. Файлы, сохраненные в volume, терялись
3. Nginx не мог найти файлы, так как они были в другом месте

## Решение

Изменили конфигурацию, чтобы **оба сервиса использовали один и тот же bind mount**:

```yaml
# Бэкенд
volumes:
  - ./media:/app/media:rw  # Bind mount вместо volume

# Nginx (уже было правильно)
volumes:
  - ./media:/app/media:rw
```

## Изменения

### 1. `docker-compose.production.yml`
- ✅ Заменен `backend_media:/app/media` на `./media:/app/media:rw`
- ✅ Удален volume `backend_media` из секции volumes

### 2. `dc.prod.yml`
- ✅ Заменен `backend_media:/app/media` на `./media:/app/media:rw`
- ✅ Удален volume `backend_media` из секции volumes

## Преимущества bind mount

1. **Сохранение файлов**: Файлы сохраняются на хосте в `./media` и не теряются при пересоздании контейнеров
2. **Синхронизация**: Бэкенд и Nginx используют один и тот же путь
3. **Простота бэкапов**: Можно легко делать бэкапы директории `./media`
4. **Прозрачность**: Файлы видны на хосте, что упрощает отладку

## Важные замечания

1. **Создайте директорию на хосте**: Убедитесь, что директория `./media` существует на сервере:
   ```bash
   mkdir -p ./media
   chmod 755 ./media
   ```

2. **Права доступа**: Убедитесь, что контейнеры имеют права на запись:
   ```bash
   # В docker-compose можно добавить user mapping или использовать chown
   ```

3. **Бэкапы**: Регулярно делайте бэкапы директории `./media`:
   ```bash
   tar -czf media_backup_$(date +%Y%m%d).tar.gz ./media
   ```

4. **CI/CD**: Убедитесь, что CI/CD не удаляет директорию `./media` при деплое

## Применение исправления

### Важно перед применением!

Если у вас уже есть файлы в Docker volume `backend_media`, их нужно перенести:

```bash
# 1. Остановите контейнеры
docker-compose -f docker-compose.production.yml down

# 2. Создайте директорию на хосте
mkdir -p ./media

# 3. Скопируйте файлы из volume (если они там есть)
docker run --rm -v jmsad_backend_media:/source -v $(pwd)/media:/dest alpine sh -c "cp -a /source/. /dest/"

# 4. Установите правильные права
chmod -R 755 ./media

# 5. Пересоздайте контейнеры с новой конфигурацией
docker-compose -f docker-compose.production.yml up -d
```

### Проверка после исправления

1. Проверьте, что директория `./media` создана и доступна:
   ```bash
   ls -la ./media
   ```

2. Проверьте, что контейнеры запущены:
   ```bash
   docker-compose -f docker-compose.production.yml ps
   ```

3. Загрузите тестовый PDF документ и убедитесь, что он сохраняется:
   ```bash
   # Проверьте, что файл появился на хосте
   ls -la ./media/evidence/  # или другой путь в зависимости от типа файла
   ```

4. После деплоя через CI/CD проверьте, что файлы остались на месте

### Для CI/CD

Убедитесь, что ваш CI/CD скрипт:
1. **НЕ удаляет** директорию `./media` при деплое
2. **Сохраняет** директорию `./media` между деплоями
3. **Создает** директорию `./media`, если её нет:
   ```bash
   mkdir -p ./media
   chmod 755 ./media
   ```

## Альтернативные решения (для будущего)

Если в будущем понадобится масштабирование или более надежное хранилище:

1. **S3/MinIO**: Использовать объектное хранилище для медиа-файлов
2. **NFS**: Сетевая файловая система для нескольких серверов
3. **GlusterFS/Ceph**: Распределенная файловая система

Но для текущего использования bind mount - оптимальное решение.
